1. SYSTEM ARCHITECTURE & HIGH-LEVEL FLOW
========================================================================================================================

The RentTrack system operates on a client-server architecture with strict separation of concerns:

  +---------------------------------------------------------------------------------------------------+
  |                                        CLIENT BROWSER LAYER                                       |
  |                                                                                                   |
  |   [Admin / Owner Operations Portal]                        [Tenant Resident Self-Service Portal]  |
  |   Next.js 15 (React 19) • Tailwind CSS                     Next.js 15 (React 19) • Tailwind CSS   |
  |   Path: /admin/*                                           Path: /tenant/*                        |
  +-------------------------------------------------+-------------------------------------------------+
                                                    |
                                         HTTPS / JSON REST API
                               (Bearer JWT Token in Authorization Header)
                                                    |
  +-------------------------------------------------v-------------------------------------------------+
  |                                         BACKEND API ENGINE                                        |
  |                                                                                                   |
  |   Runtime: Node.js v20+ / Express.js                                                              |
  |   - Security Middleware: Security Headers (CSP, HSTS), Rate Limiter, SQLi Guard, Input Sanitizer  |
  |   - Auth Guard: Token Verification, Blacklist Check, Role & Permission Evaluation (RBAC)          |
  |   - File Upload Engine: Multer Disk Storage (/backend/uploads/payments, /backend/uploads/requests)|
  |   - Domain Controllers: Auth, Admin, Tenant, Billing, Requests, Messages, Settings, Diagnostics  |
  |   - Background Cron Daemons: Billing Cycle Daemon, Overdue Watcher, Reminder Notification Engine  |
  +-------------------------------------------------+-------------------------------------------------+
                                                    |
                                      PostgreSQL Connection Pool
                                          (pg Pool Client)
                                                    |
  +-------------------------------------------------v-------------------------------------------------+
  |                                      RELATIONAL DATABASE LAYER                                    |
  |                                                                                                   |
  |   PostgreSQL 16 Server (Database: rentTrack_db)                                                   |
  |   Schema: "rentTrack_schema"                                                                      |
  |   Key Tables: users, rooms, bills, payments, requests, messages, announcements,                   |
  |               activity_logs, settings (JSONB), token_blacklist                                    |
  +---------------------------------------------------------------------------------------------------+

2. END-TO-END TENANT LIFECYCLE WORKFLOW
========================================================================================================================

2.1 Account Registration & Identity Submission
------------------------------------------------------------------------------------------------------------------------
1. Tenant opens the public application and selects "Register / Sign Up".
2. Tenant enters their full name, official email address, mobile number, emergency contact details, and password.
3. The frontend runs client-side phone validation (+63 / 09 format) and password strength validation.
4. Payload is submitted to `POST /api/auth/register`.
5. Backend hashes password using bcrypt with salt rounds = 10, sets status = 'Pending', role = 'tenant'.
6. JWT token is generated and returned; tenant is authenticated into the onboarding space.

2.2 Room Matrix Discovery & Bedspace Selection
------------------------------------------------------------------------------------------------------------------------
1. Onboarded tenant accesses the Room Discovery view (`/tenant/rooms`).
2. Tenant browses the 3-floor boarding house matrix (Rooms 101–308) with real-time occupancy badges.
3. Tenant views unit price (₱/month), capacity, occupied count, aircon/fan amenities, and bed availability.
4. Tenant selects an available bedspace and submits a reservation request to `POST /api/tenant/room/select`.
5. System checks capacity constraints: if occupied < capacity, room request is linked to the tenant's profile.

2.3 Tenancy Approval & Lease Activation
------------------------------------------------------------------------------------------------------------------------
1. Administrator receives real-time alert of the pending application.
2. Administrator reviews tenant credentials, assigns exact bedspace, and clicks "Approve".
3. Backend executes transaction: updates tenant `status = 'Active'`, links `room_id`, sets `date_moved_in`.
4. Tenant receives in-app confirmation and gain full resident portal privileges.

2.4 Daily Resident Dashboard & Tenancy Status
------------------------------------------------------------------------------------------------------------------------
1. Resident navigates to `/tenant/dashboard`.
2. Dashboard queries `GET /api/tenant/dashboard` and displays:
   - Tenancy card: Room number, bedspace, move-in date, contract period.
   - Financial card: Current balance due (₱), upcoming due date, payment status.
   - Quick action shortcuts: Settle Bill, File Maintenance Request, Direct Message Landlord.

2.5 Automated Invoicing & Statement Delivery
------------------------------------------------------------------------------------------------------------------------
1. Automated billing engine triggers based on the tenant's individual billing start date.
2. An official electronic invoice (`INV-YYYY-XXXXX`) is created in `rentTrack_schema.bills`.
3. Invoice includes: Room base tariff + water flat rate + electricity submeter reading + previous balance.
4. Tenant receives in-app billing alert 3 days before the due date.

2.6 Payment Proof Submission & E-Receipt Issuance
------------------------------------------------------------------------------------------------------------------------
1. Resident opens `/tenant/billing` and reviews unpaid balance.
2. Resident selects payment method (GCash, Maya, Bank Transfer, or Cash Counter).
3. Resident pays through the designated e-wallet/bank QR and takes a transaction screenshot.
4. Resident uploads proof image and types reference number in `POST /api/tenant/billing/pay`.
5. Status changes to "Pending Verification".
6. When verified by admin, an Official Electronic Receipt (`REC-YYYY-XXXXX`) is issued and available for download.

2.7 Maintenance Work Order Ticketing & Tracking
------------------------------------------------------------------------------------------------------------------------
1. When repairs are needed, tenant visits `/tenant/requests` and clicks "New Request".
2. Tenant fills in category (Plumbing, Electrical, Carpentry, Appliance, Other), urgency, and problem details.
3. Submits to `POST /api/requests`. System assigns collision-proof ticket ID (`RT-XXXXXX`).
4. Tenant monitors live status progression on the Kanban board: `Pending` -> `In Progress` -> `Resolved`.
5. Only the ticket author or administrator can cancel or resolve the request.

2.8 Direct Messaging & Facility Broadcast Notices
------------------------------------------------------------------------------------------------------------------------
1. Tenant visits `/tenant/chat` to communicate with management without sharing personal social media.
2. Messages are exchanged in real-time with delivery timestamps and read receipts.
3. Facility-wide announcements (water/power interruptions, curfew advisories) appear pinned on the resident stream.

2.9 Resident Profile, Security & Preferences (Settings Hub)
------------------------------------------------------------------------------------------------------------------------
1. Resident navigates to `/tenant/settings` (single whole page layout, 6 labeled categories).
2. Category 1 (My Profile): Edit name, phone, emergency contacts; review tenancy status.
3. Category 2 (Account & Security): Change password with strength meter, toggle 2FA, view active sessions.
4. Category 3 (Notification Preferences): Configure upcoming rent reminders, due date alerts, work order updates.
5. Category 4 (Appearance & Display): Select Clean Light, Obsidian Dark, or System theme; date/time formats.
6. Category 5 (Privacy & Data): View Privacy Notice, Tenancy Agreement, download personal data JSON archive.
7. Category 6 (Help & Support): Read resident FAQs, access direct landlord office phone, report app issues.

2.10 Move-Out, Clearance & Lease Termination
------------------------------------------------------------------------------------------------------------------------
1. Tenant submits move-out notice through the portal.
2. Administrator inspects room condition, verifies zero outstanding balance, and clears security deposit.
3. Tenant account transitions to 'Moved Out' / Inactive, freeing up bedspace in the Room Matrix.

3. END-TO-END ADMINISTRATOR OPERATIONAL WORKFLOW
========================================================================================================================

3.1 Daily Login, 2FA & Executive Dashboard Oversight
------------------------------------------------------------------------------------------------------------------------
1. Administrator signs in at `/login`.
2. Backend verifies email/password against `users` table and checks role (`admin` or `owner`).
3. If 2FA enabled, TOTP token challenge is verified.
4. Upon login, admin is directed to `/admin/dashboard` showing live telemetry:
   - Total Active Residents, Bedspace Occupancy Percentage.
   - Monthly Collections (₱) vs Outstanding Arrears.
   - Pending Payment Verifications counter & Pending Maintenance requests.

3.2 Room Inventory & 3-Floor Space Matrix Management
------------------------------------------------------------------------------------------------------------------------
1. Admin opens `/admin/rooms` to inspect the visual 3-floor grid.
2. Admin can:
   - Click any room card to view current occupants, capacity, and bed distribution.
   - Add new rooms or edit room tariffs (monthly rate, aircon amenities).
   - Manually assign a resident to an available bed or transfer between rooms.
   - Mark a unit under "Maintenance" to temporarily restrict new assignments.

3.3 Tenant Registry & Application Review Desk
------------------------------------------------------------------------------------------------------------------------
1. Admin navigates to `/admin/tenants`.
2. Admin reviews pending applicant cards, checks contact details and emergency info.
3. With 1-click, admin approves application, assigns room/bed, or declines with reason.
4. Admin can filter tenant roster by Room, Status (Active, Pending, Moved Out), or search by name.

3.4 Billing Operations, Tariff Policies & Submetering
------------------------------------------------------------------------------------------------------------------------
1. Admin navigates to `/admin/billing`.
2. System displays all active monthly billing cycles.
3. Admin can enter submeter utility readings (water m³, electricity kWh) for individual rooms.
4. System automatically applies standard submeter rates configured in Global Settings.
5. Admin can manually generate supplemental invoices (damage fees, key replacement).

3.5 Payment Proof Verification & Atomic Reconciliation
------------------------------------------------------------------------------------------------------------------------
1. Unverified payments appear in the "Verification Queue" on `/admin/billing`.
2. Admin clicks a payment entry to view submitted GCash/Maya screenshot and reference number.
3. Admin clicks "Verify & Approve":
   - Database starts atomic transaction: `BEGIN`.
   - Inserts approved payment into `payments` table.
   - Deducts amount from bill `balance` and updates `status = 'Paid'` (or `'Partial'`).
   - Inserts audit log entry into `activity_logs`.
   - Commits transaction: `COMMIT`.
4. System dispatches confirmation notification and E-Receipt to the resident.

3.6 Maintenance Work Order Dispatch & Contractor Tracking
------------------------------------------------------------------------------------------------------------------------
1. Admin opens `/admin/requests` featuring the interactive Kanban Board.
2. Admin reviews incoming tickets under `Pending`.
3. Admin clicks "Start Repair": ticket moves to `In Progress`, technician is assigned.
4. Upon inspection and repair completion, admin clicks "Mark Resolved".
5. Resolution timestamp and admin notes are logged, notifying tenant immediately.

3.7 Real-Time Direct Chat & Community Announcements
------------------------------------------------------------------------------------------------------------------------
1. Admin visits `/admin/chat` to view conversations grouped by resident.
2. Admin replies directly to resident questions in real time.
3. Admin clicks "Broadcast Announcement" to publish building-wide alerts.
4. Broadcast appears instantly on all resident portal dashboards and triggers push/email alerts.

3.8 Premises CCTV & Security Monitoring Matrix
------------------------------------------------------------------------------------------------------------------------
1. Admin accesses `/admin/cctv` to inspect facility monitoring feeds:
   - Camera 01: Main Entrance & Gate
   - Camera 02: 1st Floor Hallway & Reception
   - Camera 03: 2nd Floor Corridor
   - Camera 04: 3rd Floor Corridor & Emergency Exit
2. Displays live timestamp overlays, camera health status, and recording indicator.

3.9 Financial Reports, Collection Audits & Data Analytics
------------------------------------------------------------------------------------------------------------------------
1. Admin/Owner visits `/admin/reports`.
2. System computes aggregate figures across bills, payments, and rooms:
   - Gross Revenue, Net Collections, Total Outstanding Arrears.
   - Monthly Collection Rate percentage.
   - Payment method breakdown (GCash % vs Maya % vs Cash %).
   - Occupancy rate breakdown by floor.
3. Admin exports reports in structured CSV format for accountant and tax filing.

3.10 System Governance, Settings & Platform Controls
------------------------------------------------------------------------------------------------------------------------
1. Admin/Owner accesses `/admin/settings` (single whole page layout, 10 labeled categories).
2. Category 1: Property Information (Name, address, contact, operating status).
3. Category 2: Billing & Financial Rules (Rent tariffs, individual cycle, short-month rule, penalties).
4. Category 3: User Accounts & Permissions (Role delegation, RBAC, Owner safeguard).
5. Category 4: Notification Rules (Payment alerts, due dates, work orders, SMS integration).
6. Category 5: Branding & Appearance (Logo upload, primary color picker, theme modes).
7. Category 6: Security & Privacy (Password change, 2FA, session timeout, lockout limits).
8. Category 7: Data Management & Backups (Daily snapshot status, cache purge, config JSON export).
9. Category 8: Audit Logs & System Activity (Live audit trail, search, category filters, CSV export).
10. Category 9: System Preferences (Timezone Asia/Manila, date/time format, maintenance mode).
11. Category 10: Help & Support (Support hotline, email support, interactive FAQs, ticket dispatch).

4. AUTOMATED BACKGROUND & CRON ENGINE WORKFLOWS
========================================================================================================================

4.1 Individual Tenancy Billing Cycle Daemon
------------------------------------------------------------------------------------------------------------------------
- Engine: Background Node.js cron scheduler running daily at 00:00:00 midnight PHT.
- Logic:
  1. Identifies active tenants whose contract billing cycle day matches today's calendar date.
  2. Queries tenant room rental tariff and current utility charges.
  3. Verifies idempotency: checks if bill already generated for current cycle period.
  4. Generates unique invoice number (`INV-YYYY-XXXXX`).
  5. Inserts invoice into `bills` table with `status = 'Unpaid'`.
  6. Dispatches billing notification alert to tenant portal and email.

4.2 Short-Month Calendar Billing Rule Engine
------------------------------------------------------------------------------------------------------------------------
- Core Rule: Preserves original contract billing day; uses the last valid calendar day of shorter months.
- Implementation:
  * Tenant with billing date of January 31:
    - February bill generated on February 28 (or February 29 in a leap year).
    - March bill generated on March 31.
    - April bill generated on April 30.
  * Ensures tenants moving in on the 31st are never skipped during February, April, June, September, November.

4.3 Overdue Rent Auditing & Automated Penalty Application
------------------------------------------------------------------------------------------------------------------------
- Schedule: Runs every 24 hours at 01:00:00 AM PHT.
- Logic:
  1. Compares current calendar date against `due_date + grace_period_days` (default 5 days).
  2. For all bills where `status = 'Unpaid'` or `'Partial'` and grace period has elapsed:
     - Sets bill `status = 'Overdue'`.
     - Appends configured late penalty fee (₱300 or 5%) to bill balance.
     - Logs overdue penalty event in `activity_logs`.
     - Dispatches high-priority overdue alert notification to tenant.

4.4 Real-Time Resident Presence & Heartbeat Monitoring
------------------------------------------------------------------------------------------------------------------------
- Tracks active user sessions via periodic client heartbeats.
- Displays real-time "Online" status badges in admin direct chat interface.

5. STATE MACHINE & LIFECYCLE TRANSITIONS
========================================================================================================================

5.1 Room & Bedspace State Machine
------------------------------------------------------------------------------------------------------------------------
  [ Vacant Unit ] (Occupants == 0)
        |
        | (Tenant selects bedspace / Admin allocates applicant)
        v
  [ Partially Occupied ] (0 < Occupants < Capacity)
        |
        | (Additional occupants assigned until full)
        v
  [ Fully Occupied ] (Occupants == Capacity)
        |
        | (Tenant vacates / moves out)
        v
  [ Partially Occupied / Vacant ]

  * Any room can transition to [ Under Maintenance ] by admin, hiding it from applicant discovery.

5.2 Invoice & Balance State Machine
------------------------------------------------------------------------------------------------------------------------
  [ Issued / Unpaid ]
        |
        +---> (Tenant uploads payment proof) --------> [ Pending Verification ]
        |                                                     |
        |                                                     +--> (Admin Approves)
        |                                                     |         |
        |                                                     |         v
        +---> (Due date expires + grace period)               |    [ Paid / Partial ]
        |                                                     |
        v                                                     +--> (Admin Rejects)
  [ Overdue ] <-----------------------------------------------+         |
        |                                                               v
        +---> (Payment submitted and verified) ---------------->   [ Unpaid ]

5.3 Maintenance Request State Machine
------------------------------------------------------------------------------------------------------------------------
  [ Submitted / Pending ]
        |
        +---> (Admin clicks 'Start Repair') ---------> [ In Progress ]
        |                                                    |
        +---> (Author cancels before repair begins)          +--> (Admin clicks 'Mark Resolved')
        |                                                    |
        v                                                    v
  [ Cancelled ]                                        [ Resolved ]

5.4 Resident Account State Machine
------------------------------------------------------------------------------------------------------------------------
  [ Registered Applicant ]
        |
        +---> (Admin Approves Application) ---------> [ Active Resident ]
        |                                                   |
        +---> (Admin Declines Application)                  +--> (Move-Out Clearance Completed)
        |                                                   |
        v                                                   v
  [ Declined ]                                        [ Moved Out / Inactive ]

6. SECURITY, AUTHENTICATION & CRYPTOGRAPHIC POLICIES
========================================================================================================================

6.1 RFC 7519 JWT Claims & Stateless Token Verification
------------------------------------------------------------------------------------------------------------------------
All issued JSON Web Tokens follow RFC 7519 standards and contain standard payload claims:
- `iss`: "RentTrack-Auth-Server" (token issuer)
- `aud`: "RentTrack-Api-Clients" (intended audience)
- `sub`: User ID (subject)
- `jti`: Unique cryptographically random UUID per token (enables selective revocation)
- `role`: User role ('owner', 'admin', 'tenant')
- `permissions`: Granular permission array based on RBAC matrix
- `iat` / `exp`: Issue and expiration timestamps

6.2 Token Blacklisting & Immediate Session Revocation
------------------------------------------------------------------------------------------------------------------------
- Located in `backend/utils/tokenBlacklist.js`.
- When user logs out, their token's `jti` is inserted into an in-memory & database blacklist with its expiration TTL.
- Middleware verifies every incoming request against the blacklist; revoked tokens are instantly denied (HTTP 401).

6.3 Role-Based Access Control (RBAC) & Owner Privilege Protection
------------------------------------------------------------------------------------------------------------------------
- Middleware: `backend/middleware/rbacMiddleware.js`.
- Granular permissions: `rooms:read`, `rooms:write`, `tenants:read`, `tenants:write`, `billing:read`, `billing:write`,
  `payments:verify`, `maintenance:read`, `maintenance:write`, `reports:read`, `settings:read`, `settings:write`.
- Strict Privilege Boundary: Owner privileges cannot be acquired simply by toggling an admin setting. Database schema
  enforces role integrity.

6.4 SQL Injection Defense, Input Sanitization & Security Headers
------------------------------------------------------------------------------------------------------------------------
- Parameterized Queries: All database interactions utilize PostgreSQL parameterized queries (`$1, $2, ...`).
- SQLi Inspector: `backend/middleware/sqlInjectionProtector.js` inspects all incoming payloads for malicious SQL syntax.
- XSS Sanitizer: `backend/middleware/sanitize.js` strips dangerous HTML/script tags from incoming form fields.
- Security Headers: `backend/middleware/securityHeaders.js` enforces strict CSP, HSTS, X-Content-Type-Options,
  X-Frame-Options (DENY), and Referrer-Policy.
- Rate Limiting: `backend/middleware/rateLimiter.js` protects sensitive endpoints (login: 5 attempts/15min, API: 120 req/min).

7. API ROUTING & CLIENT INTERCEPTOR FLOW
========================================================================================================================

All frontend HTTP communication routes through the centralized Axios client (`frontend/src/lib/api.ts`):
1. Request Interceptor:
   - Reads JWT token from `localStorage`.
   - Injects `Authorization: Bearer <token>` into HTTP request headers.
2. Response Interceptor:
   - Catches HTTP 401 Unauthorized errors.
   - Automatically purges local credentials and redirects user to `/login`.
3. Offline Resilience:
   - Gracefully intercepts network disconnections (`ERR_NETWORK`), preventing unhandled client crashes and displaying
     friendly Sonner toast notifications.

Key Endpoint Namespaces:
- `/api/auth/*`          : Authentication, registration, login, logout, token refresh
- `/api/admin/*`         : Executive dashboard, rooms CRUD, tenant roster, billing, settings, diagnostics
- `/api/tenant/*`        : Resident profile, room reservation, payments upload, notifications
- `/api/requests/*`      : Maintenance ticketing and work order tracking
- `/api/admin/chat/*`    : Direct messaging threads and broadcast announcements

8. FILE UPLOAD & STORAGE MANAGEMENT WORKFLOW
========================================================================================================================

1. Payment Proof Receipts:
   - Uploaded via `multipart/form-data` with field name `proofOfPayment`.
   - Filtered for allowed image types: `image/jpeg`, `image/png`, `image/webp`.
   - Stored in server directory `backend/uploads/payments/`.
   - Filename format: `${Date.now()}-${tenantId}.${ext}`.

2. Maintenance Defect Photos:
   - Uploaded with field name `attachment` or `image`.
   - Stored in server directory `backend/uploads/requests/`.
   - Filename format: `${Date.now()}-${requestId}.${ext}`.

3. Static File Access:
   - Served securely through Express static middleware at `/uploads/payments/*` and `/uploads/requests/*`.
